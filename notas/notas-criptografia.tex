\subsection{STRIDE}
\label{sec:org0228619}
\begin{itemize}
\item STRIDE es un modelo de amenazas, utilizado para ayudar a razonar y encontrar amenazas a un sistema.

\item Spoofing: Suplantar la identidad en redes informaticas haciendose pasar por una persona, entidad o sistema de confianza para engañar a la victima. Se puede mitigar por firmas digitales, contraseñas, etc. -> Autenticidad

\item Tampering: Alterar, manipular o interferir con algo sin autorización, generalmente con el fin de causar daño, obtener beneficios ilegales o comprometer la integridad de un sistema, proceso o evidencia. Usa la tecnologia de hash para mitigarlo. -> Integridad

\item Repudation: El acto de negar, por parte de una persona o sistema, haber realizado una acción, transacción o comunicación especifica. -> No repudio

\item Information disclosure: Acceso no autorizado o la revelación inadvertida de datos sensibles, confidenciales o privados a personas, sistemas o entidades que no deberian tener acceso a ellos. -> Confidencialidad

\item Denegation of service: Hacer que un sistema, servicio o red sea inaccesible para sus usuarios legitimos. -> Disponibilidad

\item Elevation of privileges: Otorgar permisos a usuarios que no deben de tener dichos permisos. -> Autorizacion
\end{itemize}

\subsubsection{Funciones de hash}
\label{sec:org088ba06}
\begin{itemize}
\item Una funcion de hash toma un contenido de cualquier tamano(hasta vacio) y siempre produce un numero de un tamano fijo.
\item Por ejemplo, MD5 produce una salida de 16 bytes
\item Este tamano tiene una relacion con la seguridad de la funcion entre mas pequenos es peor.
\item Dominio -> Codominio
\item Una vez mas, las propiedades que una funcion de hash debe de cumplir son:
\begin{itemize}
\item El mismo documento siempre produce el mismo digest.
\item El digest parece aleatorio, si tienes el digest eso no te da pistas del documento de entrada.
\item Idealmente cada documento con contenido diferente deberia tener un digest diferente (lo cual en realidad no es posible).
\end{itemize}

\item Los digests son como huellas digitales: si tienes al sujeto se puede verificar que sea quien dice ser mediante su huella digital.
\item Sin embargo, si solo tiene la huella digital no es facil determinar el sujeto que la posee.
\item Es facil calcular el digests de un documento, pero si tiene solo el digest es muy dificil determinar el documento que lo produjo, entre mas dificil mejor.
\item Por esta razon son llamadas funciones de una sola via, se puede ir de entrada a la salida pero no al reves.
\end{itemize}
\subsubsection{Hashing}
\label{sec:org86349ef}
\begin{itemize}
\item En computacion, el termino funcion de hash casi siempre se refiere a una funcion criptografica.
\item Sin embargo, el termino es general
\item Por ejemplo: Una funcion hash que establece si un numero es par o impar. Esencialmente, las funciones hash relaciona elementos de un dominio muy grande, con elementos de un codominio relativamente pequeno.
\item El tamano del codominio depende de la funcion de hash, por ejemplo, ya se dijo que MD5 genera digest de 16 bytes. Cual es el tamano del codominio para MD5?
\item SI se considera un numero muy grande de documentos de entrada es posible que muchos de ellos produzcan el mismo hash.
\item Dado lo anterior, las funciones de hash tienen perdida. Se pierde informacion de la fuente al digest.
\item Que tenga perdida es importante, de lo contrario habria una forma de regresar del digest al documento original.
\item Considerando de nuevo la funcion par
\item Cualquier numero puede dar como resultado 0 (par) o 1 (inpar)
\item Seria posible saber, dado un valor 0 o 1que numero produjo dicho resultado
\item Esta funcion tiene todas las propiedades: tienen perdida, comprime la entrada y es consistente ya que dada la misma entrada siempre produce la misma salida.

\item Las propiedades de consistencia, compresion y perdida son comunes en cualquier funcion de hash pero no suficientes para ser seguras o criptograficas.
\item Se requieren las sig. propiedades:
\begin{itemize}
\item Resistencia de preimagen.
\item Segunda resistencia de preimagen.
\item Resistencia de colisiones.
\end{itemize}
\end{itemize}
\begin{enumerate}
\item Resistencia de preimagen
\label{sec:orgd22355d}
\begin{itemize}
\item Una preimagen es el conjunto de entradas de una funcion de hash que producen, en el caso de par o impar, una preimagen son todos los numeros pares que den valor 0.
\item Una preimagen de una funcion de hash H y un valor de hash k es el conjunto de valores x por el cual H(x) = k

\item Al tener un digest, existe un numero infinito de documentos que produjeron dicho digest.
\item Eso no quiere decir que dado un digest sea facil encontrar un elemento de la preimagen

\item La resistencia de preimagen es basicamente: si tengo un digest y no se como se obtuvo, no pudo ni siquiera encontrar un elemento en la preimagen sin realizar una cantidad ridicula de trabajo computacional.

\item Intratable -> Se puede resolver, pero cuesta demasiado
\item No computable -> No se puede resolver con una computadora
\item Idealmente, los elementos de la preimagen deberian estar muy separados entre ellos y no tener un espaciado predecible
\item El hecho de que las funciones de hash tengan perdida ayuda a la resistencia de preimagen
\item Si una funcion de hash tiene buena resistencia de preimagen, los ataques en este sentido seran aleatorios o bien consistiran en enumeraciones muy largas (fuerza bruta) hasta encontrar una coincidencia, lo cual no es computacionalmente tratable.
\item Al proceso de intentar encontrar un elemento de la preimagen dado un valor de hash se le llama invertir el hash
\item Encontrar un inverso deberia ser muy dificil.
\end{itemize}
\item Segunda resistencia de preimagen
\label{sec:orgf5aeb48}
\begin{itemize}
\item Si tu tienes al menos un documento que produce un hash conocido, sigue siendo muy dificil encontrar otro documento que produzca el mismo hash.
\item Esto funciona porque no existe patron repetible en los elementos de la preimagen.
\end{itemize}
\item Resistencia a colisiones
\label{sec:orga296d27}
\begin{itemize}
\item Significa que es dificil encontrar dos entradas que produzcan el mismo hash y garantiza que sea computacionalmente inviable encontrar dos entradas diferentes que produzcan el mismo valor hash.
\item No un hash especifico sino cualquier hash.
\item Es mas facil encontrar una colision en un hash cualquiera que encontrar un elemento de la preimagen de un hash dado.
\item Propiedad avalancha: El valor de hash cambia drasticamente y de forma impredecible, un minimo del 50\% de los bits del hash deberia ser diferente.
\end{itemize}
\end{enumerate}

\subsubsection{AES}
\label{sec:org8fbe865}
\begin{itemize}
\item Advanced Encryption Standard
\item Lo utiliza TLS (HTTPS) y funciones de cifrado de sistemas de archivos de un OS.
\item AES es un cifrador de bloque, cifra por bloques de 16 bytes, si no cumple con los 16 bytes se debe de agregar un padding (datos de relleno).
\item Tambien puede cifrar un byte a la vez, esto se concoe como cifrado de flujo y no necesitan padding.
\item En general, es mas eficiente cifrar bloques que en flujo.
\end{itemize}
\begin{enumerate}
\item Modos de operacion de AES
\label{sec:org9fc050c}
\begin{enumerate}
\item ECB - Electronic Code Book
\label{sec:org9f8f37c}
\begin{itemize}
\item Cualquier texto plano de 16 bytes tiene 16 bytes correspondientes de salida.
\item Cada bloque es tratado independientemente, esa es su debilidad.
\begin{itemize}
\item Puede generar un ataque de texto plano escogido, que se basa en tener muchos mensajes de estructura parecida para enganar con un mensaje falso con una respuesta predecible.
\end{itemize}
\item Parametros: Texto plano y llave.
\end{itemize}
\item CBC - Cipher Block Chaining
\label{sec:org26954ef}
\begin{itemize}
\item Despues de cifrar el bloque aplicar una funcion XOR con el siguiente bloque en texto plano, el resultado se cifra y se guarda ese bloque. Para descifrar se tiene que invertir el proceso.
\item Para el primer bloque a cifrar, se utiliza el IV dado que no hay un bloque anterior para hacer XOR, el IV debe de ser del mismo tamano del bloque (16 bytes).
\begin{itemize}
\item Parametros: Texto plano, llave e IV
\item Debe de tener su respectivo padding.
\end{itemize}
\end{itemize}
\item CTR - Counter Mode
\label{sec:org9618abb}
\begin{itemize}
\item No requiere de padding
\item Genera un key stream de cualquier longitud a partir de una llave AES de al menos 128 bits (16 bytes), luego aplica XOR para combinarlos.
\item CTR incrementa el contador en uno y asi sucesivamente. Si el texto plano no es multiplo de 16, los ultimos 16 bytes del key stream se truncan para corresponder al texto.
\item Al IV se le llama nonce.
\item CTR puede cifrar de forma independiente.
\item Parametros: key, nonce, texto plano.
\end{itemize}
\end{enumerate}
\end{enumerate}
\subsubsection{Seguridad en cifrado simetrico}
\label{sec:org5d34636}
\begin{itemize}
\item Para tener un cifrado seguro y efectivo se necesita:
\begin{enumerate}
\item Cifrar el mismo mensaje de forma diferente cada vez que se haga, aunque se use la misma
llave.
\item Eliminar patrones predecibles entre los bloques. (Maleabilidad entre bloques)
\end{enumerate}

\item Para resolver el primer problema, se utiliza un vector de inicializacion (IV), el cual es una cadena aleatoria externa al texto plano y la llave. El IV es publico ya que solo hace que los mensajes no sean repetibles y no generar patrones.
\item Nunca debe reusarse el mismo IV
\item Existen ataques donde si conoces el texto plano y el IV (suponiendo que lo reutilizan) puedes obtener el key-stream.
\end{itemize}

\item HMAC
\label{sec:orgefba13e}
\begin{itemize}
\item Hash-based Message Authentication Code
\item Es basicamente un hash keyed
\item Las funciones de hash son deterministas, dada la misma entrada siempre se produce la misma salida.
\item Solo agregar al inicio o al final
\item H(K XOR opad + H((K XOR ipad)+ text))
\begin{itemize}
\item H es la funcion de hash
\item K es la llave que debe de cumplir ciertos requisitos
\item text es cualquier binario que representa el contenido de entrada
\item opad e ipad son dos valoresi
\item B es el tamano del bloque de H (128 bytes)
\begin{enumerate}
\item Si K es mas corto que B, entonces a K se le tienen que agregar ceros de padding hasta ser de longitud B.
\item Si K es mas largo que B, entonces K se reduce aplicando H a K, osea H(K)
\item Si se aplico 2 y la llave quedo muy corta, entonces se aplica 1
\end{enumerate}
\item Si se aplica lo anterior, siempre se va a tener una llave de longitud B.
\item ipad se define com el byte 0x36 repetido B veces
\item opad es el byte 0x5c repetido B veces
\item Los pads parecen arbitrarios pero tienen un sentido de seguridad matematico que ayuda a mitigar
\end{itemize}

\item CBC-MAC
\label{sec:org2fd3a68}
\begin{itemize}
\item Similar a AES-CBC
\item Recordar que CBC es Cipher Block Chaining
\item Un MAC a menudo se le llama ``tag'' (mensaje) del mensaje
\item Es info extra que se asocia al principio del contenido
\item En notacion matematica un tag se denota a menudo como t
\item Asi, un MAC sobre un mensaje m1 produce un tag t1
\item El par (m1, t1) es transmitido al receptor para ser verificado

\item AES solo puede cifrar 128 bits de bloque a la vez.
\item AES-CBC encadena la salida de un bloque cifrado con el siguiente bloque.
\item Si se altera uno se alteran todos los bloques siguientes.
\item El ultimo bloque de CBC es en si un MAC.
\end{itemize}

\item MAC Prepend Attack
\label{sec:org9237df5}
\begin{itemize}
\item Es posible mandar un mensaje manipulado y hacer que parezca que es el mensaje M1 o M2, suponiendo que esten generados por la misma llave.
\item M3 es una mezcla de M1 y M2.
\item No es necesario conocer la llave de MAC.
\end{itemize}
\begin{enumerate}
\item Proceso de ataque, anteponiendo M1 a M2
\label{sec:orgcc1b0b2}
\begin{itemize}
\item Recuperar el primer bloque de M2, denominado M21 (como es AES se toman los primeros 16 bytes)
\item Recuperar el resto de bloques de M2, denominado M2r
\item Obtener M'2 = t1 XOR M21
\item M3 = M1 + M'2 + M2r (+ significa concatenacion)
\item Con esto t3 = t2

\item Basicamente lo que hace el atacante es reemplazar el primer bloque de M2 por uno manipulado.
\item La victima vera todo el mensaje M1 completo (con su padding), un bloque que se vera posiblemente corrupto y el mensaje M2 sin su primer bloque.
\end{itemize}
\begin{enumerate}
\item Soluciones
\label{sec:org7a1db12}
\begin{itemize}
\item Agregar siempre la longitud del mensaje al inicio. Esto ayduara a corroborar si hay información extra.
\item Si se cifraron los datos usando AES-CBC, no se debe usar la misma llave para cifrar ni para obtener el MAC.
\item El IV debe ser diferente a un valor de cero.
\end{itemize}
\end{enumerate}
\end{enumerate}
\end{enumerate}

\subsubsection{Firmas digitales}
\label{sec:org8abbd1a}
\begin{enumerate}
\item RSA
\label{sec:org0323ffd}
\begin{itemize}
\item Dado que los MAC usan llaves simetricas, si se compromete la llave puede ambos lados estan en riesgo de spoofing (usurpación de identidad).
\item Las firmas intentan mitigarlo mediante criptografia asimetrica. Ya que nos existen llaves ``compartidas''.
\item La llave publica solo se puede descifrar con la llave privada y vise-versa.
\item Si se cifra con la llave privada, puede ser descifrado por la llave publica.
\item Tambien pueden usarse para firmar listas de revocación de certificados CRL's.

\item Autenticidad en reversa: El receptor no sabra de quien es el mensaje pero el emisor sabe que solo podra ser procesada por la entidad autorizada.

\item Existen muchos problemas con el cifrado asimetrico (RSA), es ineficiente para archivos grandes, no viene comprobación de integridad y solo puede procesar archivos del tamaño de modulo (2048 bits).

\item Para solucionar eso, se hace lo siguiente: Cifrar el hash del mensaje, dando tanto integridad como autenticidad.
\begin{enumerate}
\item Calcular el hash del mensaje.
\item Cifrar el hash mediante la llave privada, este hash cifrado es la firma del emisor.
\item El receptor calcula el hash del mensaje, descifra la firma mediante la llave publica y comprueba que coincidan ambos hashes.
\end{enumerate}

\item La firma debe de aplicarse siempre al texto plano, nunca al cifrado.

\item El cifrado con la llave publica es confidencialidad.
\item El cifrado con la llave privada es autenticidad.

\item El padding para firmas RSA es PSS.

\item Es comun usar tecnicas asimetricas al inicio de la comunicación para el establecimiento de confianza e intercambio de llaves simetricas. Despues todo el proceso se hace con llaves simetricas.
\end{itemize}
\end{enumerate}

\begin{itemize}

\item La identidad del propietario puede ser un nombre, email, URL, etc.
\end{itemize}
\item Firma digital sobre todo el contenido del certificado
\item Firma por la entida de confianza (issuer)

\begin{enumerate}

\item La entidad de confianza recibe la llave publica y genera el certificado

\item El cliente le pide al servidor que firme el dato.
\item El servidor firma el dato y regresa la firma.
\item El cliente comprueba la firma con la llave publica.
\end{enumerate}

\subsubsection{Diffie-Hellman DH}
\label{sec:orgc660f7d}
\begin{itemize}
\item Criptografia asimetrica
\item Una variante es con curvas elipticas ECDH
\item Intercambia parametros publicos para computar simultaneamente la misma llave en ambos lados, esto se llama Key Agreement

\item Primero crea un par de numeros matematicos, uno privado y publico. Esto para cada participante.
\item Ambas partes intercambian sus numeros publicos.
\item Con el numero publico externo y el numero privado local se genera la misma llave compartida en ambos lados.

\item El resultado es una llave simetrica o un dato que permite derivar una llave simetrica.
\item Requiere comunicación bidireccional.
\item Los parametros de DH deben ser iguales
\begin{itemize}
\item Tamaño de la llave (2048)
\item Generador (2, 5)
\end{itemize}

\item Se recomienda usar HKDF para derivar la llave
\item DH no tiene autenticación integrada
\item Una o ambas partes deben de firmar publicos intercambiados.

\item Son preferiables para el transporte de llaves antes que RSA.
\item Principalmente porque ofrecen ``Confidencialidad hacia delante'' (Forward Secrecy) dada la naturaleza de las llaves efimeras, si una llave es comprometida, no se revela nada acerca de comunicaciones previas.

\item A veces para establecer un canal de confianza necesitas transmitir datos con poca protección (pueden ser manipulados)
\item Eventualmente se llega a tener un canal que se cree protegido (ya se hizo bien el intercambio de llaves)
\item Mientras tanto se fueron calculando hashes de todos lo que se transmitio
\end{itemize}
\begin{enumerate}
\item Autenticación con DH y ECDH
\label{sec:orga6cdb43}
\begin{itemize}
\item El intercambio de llaves requiere una llave publica RSA o ECDSA, con su certificado firmado. Se usan para establecer identidad de cada parte, firmando info efimera durante el proceso de generación.
\item Ademas se agrega challenge-response.
\end{itemize}
\end{enumerate}

\subsubsection{Handshake}
\label{sec:orgffc6877}
\begin{itemize}
\item Tiene como objetivos: establecer identidad y derivar llaves de sesión para el transporte seguro.
\end{itemize}
\begin{enumerate}
\item TLS - 1.2
\label{sec:org4bb8692}
\begin{enumerate}
\item Comienza con un cliente enviando un mensaje hello al servidor. Este mensaje contiene info de configuración, tipo nonce. Tambien esta la lista de Cipher Suites.
\begin{itemize}
\item El objetivo es ponerse de acuerdo en cuanto al algoritmo y protocolos criptograficos a usar. La Cipher Suite da opciones.
\item La seguridad depende del Cipher Suite usado.
\item El chiper suite incluye:
\begin{itemize}
\item Intercambio de llaves
\item Firma digital
\item Cifrado en masa
\item Hashing
\end{itemize}
\end{itemize}
\item El servidor recibe un hello cliente, escoge uno de los cipher suites propuestos del cliente. Cuando escoge uno, envia una respuesta con la siguiente info:
\begin{itemize}
\item Hello con nonce aleatorio del servidor
\item Certificado del servidor
\item Parte publica del intercambio de llaves DHE O ECDHE, en caso de usarse Diffie-Hellman y no RSA.
\end{itemize}
\item El cliente hace el proceso como auntenticar al servidor, derivar la llave y empezar a enviar datos cifrados.
\begin{itemize}
\item TLS solo autentica el servidor, el cliente no envia un certificado para autenticarse.
\item Cuando ambas partes se autentican con un certificado se le llama Mutual TLS o MTLS.
\item Para autenticar al cliente se usa mas la identidad del usuario como user-password entre otros. Esto despues de establecer una sesión segura con una llave compartida.
\end{itemize}
\item El handshake no genera una llave en si, sino un PMS (pre-master-secret) junto a otros datos (nonce de ambas partes) para obtener el master secret.
\begin{itemize}
\item Este master secret se usa para generar las llaves de sesión para la comunicación en masa.
\item En el caso de usar RSA, no es necesario usar firmas dado que se envian las llaves publicas (en los certificados).
\item Mientras que DHE y ECDHE se derivan de manera simultanea y efimera. Ademas que debe de ser autenticado, al menos del lado del servidor, usando la llave privada del servidor de larga duración (RSA o ECDSA). El cliente cuando recibe los datos firmados usa la llave publica en el certificado del servidor para verificar la firma.
\item Es recomendable usar DH/ECHD siempre.
\end{itemize}
\item Finalizado el intercambio de llaves, toda la info debera ir cifrada y autenticada.
\item El cliente envia un mensaje llamado ``ChangeCipherSpec'' que indica que todos los mensajes siguientes usaran el CipherSuite negociado.
\item El servidor contesta con su propio CHangeCipherSpec.
\item Finalmente, cada parte manda un mensaje ya cifrado ``Finished'' que completa el handshake. Este finished contiene todos los hashes del handshake enviado. Asegurando que ningun atacante altero alguna parte del handshake.
\begin{itemize}
\item En caso que no pase la comprobación, se cierra el canal dado que esta comprometido.
\end{itemize}

\item TLS segmenta las transmisiones en paquetes, cada paquetes esta cifrado y autenticado, ademas, estan estructurados en un formato llamado TLSCipherText.
\item Son de 16 kilobytes y son similares al struct de C.
\end{enumerate}
\begin{enumerate}
\item Derivación de llaves
\label{sec:org61dc098}
\begin{itemize}
\item El PMS se expande al master secret usando una función pseudo-aleatoria (PRF), que toma un secreto y lo expande a mas bytes, usando un mecanismo HMAC-SHA256 para expandir bytes de entrada a un tamaño arbitrario.
\item El PMS se expande hasta 48 bytes para generar el master secret.
\item El master secret tambien se expande (usando PRF) a tantos bytes sea necesario para obtener las llaves de sesión e IV's requeridos.
\item Del master secret se obtiene el key\textsubscript{block} que varia del tamaño dependiendo del cipher suite.
\item El key\textsubscript{block} tiene maximo 6 parametros, esto depende del Cipher Suite:
\begin{itemize}
\item Cliente MAC key
\item Servidor MAC key
\item Cliente cifrado key
\item Servidor cifrado key
\item Cliente IV
\item Servidor IV
\end{itemize}
\end{itemize}
\end{enumerate}
\item TLS - 1.3
\label{sec:org3dcef18}
\begin{itemize}
\item Desecha la mayoria de cipher suits, quedando solo 5 que estan basados en AEAD.
\item RSA ya no se usa para transporte de llaves.
\item Solo DHE y ECDHE.
\item El handshake se hace en una sola ronda de mensajes.

\item Cliente envia su Hello junto a Cipher Suites y su llave publica (ECDH).
\item El servidor recibe el Hello del cliente, envia al cliente su Hello con la elección del Cipher Suite, su llave publica, el certificado del servidor, la firma del certificado y el finished.
\item El cliente recibe todo lo anterior del servidor y envia su finished.

\item TLS 1.3 elimina la latencia de transmisión.
\end{itemize}

\subsubsection{Ataques a TLS}
\label{sec:org9bd3261}
\begin{itemize}
\item Padding Oracle On Downgrade Legacy Encryption: TLS 1.0 puede ser explotado cuando se usa CBC. En caso de usarse 1.1 o 1.2, se puede re-negociar para usar el protocolo 1.0.
\begin{itemize}
\item Deshabilitar TLS 1.0 y 1.1
\item Verificar TLS 1.2 mediante una herramienta de auditoria
\item Migrar a TLS 1.3
\end{itemize}

\item Se forzo al servidor a bajar de versión para tener cipher suites debiles.

\item Logjam: El hello-client es interceptado y cambia la lista del cipher suite a sus versiones EXPORT de DH.
\item EXPORT: Son algoritmos debiles en la cipher suite dado que eran exportadas a otros gobiernos.
\item FREAK: Ataca al transporte de llaves RSA usando versiones export.
\begin{itemize}
\item Deshabilitar Cipher-suites debiles, en especial versiones EXPORT
\item Usa clientes que no acepten parametros debiles en DH/ECDH o RSA.
\end{itemize}

\item Sweet32: Para cifradores de bloques de 64 bits como 3DES. Impacta en los datos que se pueden cifrar con la misma llave antes de repetirse en diferentes bloques. Dado que el limite es 32 Gb.
\begin{itemize}
\item Deshabilitar cualquier cipher suite que use 3DES o cifradores de bloque de 64 bits.
\end{itemize}

\item Return Of Bleichenbacher's Oracle Threat (ROBOT): Aprovecha las vulnerabilidades de padding en PKCS 1.5 para RSA.
\begin{itemize}
\item Deshabilitar todos los cipher suites que usen RSA para intercambio de llaves.
\end{itemize}

\item Existe un problema con la compresión que revela información a los atacantes, esto en la versión 1.2.

\item Compresion Ratio Info-Leak Made Easy (CRIME):La compresión sólo funciona si hay datos repetidos, si tu sólo tienes un texto cifrado que contiene un texto comprimido y si puedes insertar o parcialmente insertar mensajes para ver el efecto de la compresión y notas que la compresión a mejorado con la inserción del mensaje, eso quiere decir que agregaste algo repetido en el mensaje original
\item TIME: Es mas efectivo que CRIME.
\item BREACH: Ataca tambien la compresión para revelar información.
\begin{itemize}
\item Deshabilitar compresión.
\end{itemize}

\item Heartbleed: Hace una petición de heartbeat excediendo el tamaño real, pudiendo leer la memoria y su contenido.
\begin{itemize}
\item Mantener las bibliotecas y aplicaciones actualizaciones.
\end{itemize}
\end{itemize}
