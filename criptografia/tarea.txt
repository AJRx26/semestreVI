# 1. ¿En qué consiste el ataque?

El ataque descrito es un **ataque de texto cifrado elegido adaptativo (adaptive chosen-ciphertext attack, CCA2)** contra RSA cuando se usa el esquema de relleno PKCS#1 v1.5.

## Idea central

El atacante **no necesita descifrar directamente**, sino que aprovecha una “fuga de información mínima”:
un **oráculo** que responde solo **sí/no** a la pregunta:

> “¿El mensaje descifrado tiene formato válido PKCS#1?”



---

## Mecanismo del ataque (intuición)

1. El atacante intercepta un ciphertext ( c ).
2. Genera nuevos ciphertexts modificados:
   [
   c' = c \cdot s^e \mod n
   ]
3. Envía ( c' ) al servidor (oráculo).
4. El servidor responde:

   * ✔ válido PKCS
   * ❌ inválido

---

## ¿Por qué esto rompe RSA?

Porque el formato PKCS#1 v1.5 impone una estructura:

```
00 || 02 || padding || 00 || datos
```

Esto implica que el mensaje descifrado debe estar en un rango:

[
2B \leq m < 3B
]

El atacante usa esta condición como una **restricción matemática** para:

* Reducir el espacio de posibles valores de ( m )
* Refinar iterativamente el intervalo
* Hasta recuperar el mensaje completo

---

## Resultado

Con suficientes consultas al oráculo (≈ (2^{20})):

✔ Se puede **descifrar el mensaje completo**
✔ Sin conocer la clave privada
✔ Solo usando respuestas binarias (sí/no)

---

# 2. ¿Qué sistemas son vulnerables?

El ataque afecta a cualquier sistema que cumpla estas condiciones:

## 1. Uso de RSA con PKCS#1 v1.5 (relleno determinista estructurado)



---

## 2. Existencia de un “oráculo”

Esto ocurre cuando el sistema:

### a) Devuelve errores distintos

Ejemplo:

* “Padding inválido”
* “Firma incorrecta”

👉 Esto filtra información crítica


---

### b) Diferencias de tiempo (timing attack)

Si:

* Padding válido → tarda más (porque verifica firma)
* Padding inválido → falla rápido

👉 El tiempo se vuelve el oráculo


---

### c) Protocolos reales (ejemplo clave)

El paper menciona explícitamente:

* SSL 3.0

Durante el handshake:

* El cliente envía un “pre-master secret” cifrado
* El servidor responde distinto si falla el padding

👉 Esto permite el ataque sin completar el protocolo


---

## 3. Casos típicos vulnerables

* Implementaciones antiguas de TLS/SSL
* APIs de criptografía mal diseñadas
* Servidores que:

  * Validan padding antes que integridad
  * Filtran errores
  * No usan esquemas modernos

---

# 3. ¿Cómo se puede evitar el ataque?

El paper da varias recomendaciones importantes:

---

## ✔ 1. No filtrar información (CRÍTICO)

* No distinguir entre errores
* No dar mensajes específicos
* No revelar timing

👉 Todas las fallas deben verse iguales


---

## ✔ 2. Verificar integridad correctamente

El orden importa:

❌ Incorrecto:

```
descifrar → revisar padding → luego integridad
```

✔ Correcto:

```
descifrar → verificar integridad inmediatamente
```

Incluso mejor:

```
verificar antes de descifrar (si es posible)
```



---

## ✔ 3. Usar esquemas seguros contra CCA

El autor lo dice explícitamente:

> usar esquemas “plaintext-aware”



---

## ✔ 4. No usar PKCS#1 v1.5 para cifrado

Este es el problema raíz:

* Padding predecible
* Estructura explotable

# 4. ¿Qué tienen que ver las conclusiones con OAEP?

Aquí está la parte más importante conceptualmente.

---

## ¿Qué es OAEP?

Optimal Asymmetric Encryption Padding

Es un esquema de padding moderno para RSA basado en:

* Aleatoriedad fuerte
* Funciones hash
* Seguridad demostrada contra CCA

---

## Conexión directa con el paper

El paper menciona:

> “Version 2 of PKCS #1 … is not susceptible to the attack”



👉 Esa versión incluye OAEP.

---

## ¿Por qué OAEP evita el ataque?

### 1. No hay estructura fija explotable

En PKCS#1 v1.5:

```
00 02 ...
```

En OAEP:

* El mensaje está enmascarado con funciones hash
* No hay patrones detectables

---

### 2. No existe un “oráculo útil”

Incluso si el sistema responde:

* válido / inválido

👉 No puedes derivar información útil del mensaje

---

### 3. Seguridad formal

OAEP está diseñado para ser:

✔ Seguro contra chosen-ciphertext attacks (CCA2)
✔ Basado en pruebas matemáticas (modelo de oráculo aleatorio)

---

## Relación conceptual profunda

El ataque de Bleichenbacher:

➡ Demuestra que **RSA + padding ingenuo ≠ seguro**

OAEP:

➡ Surge como respuesta directa a ese problema

# 1. ¿En qué consiste el ataque?

El ataque de Daniel Bleichenbacher es un **ataque adaptativo de texto cifrado elegido (CCA2)** contra RSA con PKCS#1 v1.5 que explota **una fuga mínima de información estructural**.

---

## 🔬 Núcleo del ataque (visión profunda)

El atacante NO rompe RSA directamente.
Rompe algo más sutil:

> **La validación del formato del mensaje después del descifrado**

El sistema actúa como un **oráculo de validez de padding**:

[
\mathcal{O}(c) =
\begin{cases}
1 & \text{si } Dec(c) \text{ cumple PKCS}\
0 & \text{en otro caso}
\end{cases}
]



---

## 🧠 Insight clave

El ataque se basa en dos propiedades fundamentales de RSA:

### 1. Multiplicatividad

[
c' = c \cdot s^e \mod n
\Rightarrow
m' = m \cdot s \mod n
]

👉 Puedes transformar el mensaje SIN conocerlo.

---

### 2. Estructura rígida de PKCS#1 v1.5

Un mensaje válido cumple:

```text
00 || 02 || PS || 00 || D
```

Esto implica una restricción matemática:

[
2B \leq m < 3B
]



---

## ⚙️ Cómo se explota esto (intuición avanzada)

El atacante hace lo siguiente:

1. Toma el ciphertext original ( c )
2. Genera:
   [
   c' = c \cdot s^e \mod n
   ]
3. Consulta al oráculo

Si responde “válido”:

[
2B \leq m \cdot s \mod n < 3B
]

Esto implica:

[
\frac{2B + rn}{s} \leq m \leq \frac{3B - 1 + rn}{s}
]

---

## 🧩 Reducción iterativa del espacio

Cada consulta:

👉 Reduce el rango posible de ( m )

El ataque mantiene:

[
M_i = \text{conjunto de intervalos posibles}
]

Y en cada iteración:

* Interseca restricciones
* Reduce el espacio
* Hasta llegar a un único valor

---

## 📉 Resultado final

Después de suficientes consultas:

* Se obtiene exactamente ( m )
* Sin nunca descifrar directamente

📌 El paper estima:

* ~(2^{20}) consultas (≈1 millón)

Un sistema es vulnerable si:

### ✔ Usa RSA con PKCS#1 v1.5

### ✔ Filtra información sobre el padding

## ⚠️ Tipos de fugas (muy importante)

### 1. Errores explícitos

Ejemplo:

* “Padding incorrecto”
* “Firma inválida”

👉 Diferenciar errores = oráculo perfecto


---

### 2. Errores implícitos (timing)

Diferencia:

* Padding inválido → rechazo inmediato
* Padding válido → proceso adicional

👉 El tiempo revela el bit


---

### 3. Flujo del protocolo

El caso más famoso:

* SSL 3.0

Durante el handshake:

* Cliente envía secreto cifrado
* Servidor responde distinto si falla padding

👉 El atacante no necesita autenticarse
👉 Solo necesita observar respuestas

---

## 🧨 Conclusión crítica

No es un bug específico:

👉 Es una **clase completa de vulnerabilidades**

Hoy se conocen como:

* Padding Oracle Attacks
